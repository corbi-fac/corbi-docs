The stories: today's gap, and how each is proved

Proof methods come from AGENTS.md: app is a logged manual Blender run, and unit is a test with the scripted model and a recorded scene. Nothing in a test needs a running Blender or a live LLM.

Shape it by chat Context · Guides

A1

Every run starts from the current scene

Before each prompt, Corbi reads what's in Blender and gives it to the model, so a follow-up edits what's there instead of building a second copy.

Today Follow-ups can already work: the whole chat goes back to the model, and it can call get_scene_info. Nothing makes it look first, so it may add a second building instead of editing the first.

  1. The model's input for a run includes a summary of the scene's objects: name, size, positionunit
  2. After "a 4-storey block, 20 by 12 metres", the follow-up "make it 6 storeys" leaves one object, now 6 storeys tallapp
  3. With Blender closed, a follow-up still gets an answer, without a scene summaryunit

Shares the scene reader with B1

A2

Refer to each building by name

Each building Corbi makes has a readable name, so "make the tower taller" changes only the tower.

Today get_scene_info already returns object names, but nothing asks the model to name what it builds, so objects get Blender defaults such as Cube.001.

  1. The system prompt tells the model to name every object by its role, such as "Tower" or "Block A"code
  2. Objects created in a run have readable names, not Blender defaultsapp
  3. With a tower and a podium in the scene, "make the tower 10 storeys" changes only the towerapp

Depends on A1

A3

Big builds go in small steps that are safe to repeat

A large request, such as a detailed landmark, is built one part at a time, so Blender never freezes and a retry never duplicates geometry.

Today In UAT, one long script for a detailed building froze Blender, which runs every script on its main thread, until the 30-second bridge timeout. A blind retry would have built the same geometry twice. Nothing tells the model to keep scripts short.

  1. The system prompt tells the model to build one part per script (a block, a tower, a façade), to put each part in its own named collection, and to clear that collection before rebuilding itcode
  2. A timed-out script reaches the model as "Blender may still be running", not as a plain failureunit
  3. A detailed building, such as a cathedral, finishes without a timeout, and asking for it again leaves one copyapp

Blocked on the script time decision

Check what was built Sensors

B1

Corbi checks every change it makes and fixes its own mistakes

After every change in Blender, Corbi reads the scene back and checks it, so it notices its own mistakes and fixes them before answering.

Today A bpy error already comes back to the model as a failed tool result. Code that runs without error but builds the wrong thing is never checked.

  1. After a scene-changing tool call, the checks run before the model's next turnunit
  2. After a call that failed or timed out, Corbi waits until Blender answers, then reads the scene, so the model sees what was actually built before it retriesunit
  3. An object below ground, with no volume, or with a side over the size limit fails, and the model's next turn sees the reportunit
  4. A change that passes every check adds nothing to the model's contextunit
  5. The checks run in tests against a recorded scene, without Blender or a live LLMcli

B2

Answers quote the figures measured in Blender

Corbi's answers give the height, footprint, storeys and floor area measured from the geometry, not figures the model came up with.

Today Nothing is measured. Any height or area in an answer is the model's own claim.

  1. For a 20 × 12 m block 14 m tall, the report gives a 240 m² footprint and 4 storeys at 3.5 munit
  2. The final answer quotes the measured figuresapp
  3. The measurement runs in tests without Blendercli

Finish a run cleanly Termination

C1

Every run ends within a step and time limit, and says why

A run can't loop forever. When it stops early, the architect is told why and loses nothing.

Today The only cap is LangGraph's default recursion limit of 10,007 steps, which in practice means no limit. There's no time limit, and every run reports completed.

  1. A scripted model that always asks for a tool stops at the step limit with reason step_limitunit
  2. A run past the time limit stops with reason timeoutunit
  3. After an early stop, the chat rows and the save are writtendb
  4. A run whose model answers without tool calls ends with completed, as nowunit
  5. POST /agent/run returns the reason, and the chat says why when it isn't completedapi

Blocked on limit figures

C2

Stop a run that is going the wrong way

A Stop button ends a run within a few seconds and keeps what it had done.

Today A run can't be interrupted. Closing the tab doesn't stop it: the run carries on on the server.

  1. Pressing Stop ends the run with reason cancelledbrowser
  2. The chat up to the stop is stored and the scene is saveddb
  3. The next prompt runs normallybrowser

Depends on C1

C3

Corbi stops and asks when the same check keeps failing

If Corbi can't fix something, it asks the architect what to do instead of using up the step limit.

Today A run that keeps failing carries on until the model gives up or something errors.

  1. The same check failing on three turns in a row ends the run with reason stuckunit
  2. The answer names the failing check and asks how to proceedunit
  3. A check that fails once and then passes doesn't stop the rununit

Come back to my work Memory · saves

D1

See a save after every answer that changed Blender

Each answer that built something shows its save in the chat, so the architect can see their history and pick a point to go back to.

Today Every answer already saves a .blend and a models row. The chat doesn't show them, there's no endpoint to list a session's saves, and each save is stamped before its own turn's messages.

  1. In a run, every chat row's created_at is at or before its save'sdb
  2. GET /sessions/{id}/models lists the saves oldest firstapi
  3. Each answer that saved shows a save marker, including after a project is reloadedbrowser
D2

Blender always shows this session's own file

A new project or session starts in an empty Blender file, and opening one puts its latest save back. One project's model never ends up in another's file.

Today Blender keeps whatever it had open. In UAT, a new model was added into another project's open file, and the save then copied the whole mixed scene into the new project. Loading a project brings back its chat but not its model.

  1. Starting a project or a session opens an empty Blender fileapp
  2. Opening a session opens its latest save, and its first save afterwards contains only that session's objectsapp
  3. Opening a file is done by the API and isn't a tool the model can callcode
  4. With Blender closed, the project still loads and the chat says the file wasn't openedbrowser

Depends on D1

D3

Carry on from an earlier save in a new session

The architect picks an earlier save from the chat and continues from there. The original session stays as it was, and no table is added.

Today There's no way to go back. Bookmarks name a session but don't freeze or restore anything.

  1. Picking an older save creates a session with the chats up to that save and a copy of its filedb
  2. Blender opens the copy and the next prompt runs in the new sessionapp
  3. The original session's chats and saves are unchangeddb
  4. Picking the latest save creates no sessionapi

Follow along Progress feed · sessions

E1

See only my session's steps, with failures marked

While Corbi works, the architect sees only their own session's steps, and a step that failed is marked as failed.

Today Steps already show as compact lines, apart from answers. But the feed is one list for the whole app, so every open tab sees every session's steps, and a failed tool call looks the same as one that worked.

  1. Two sessions open in two tabs each see only their own stepsbrowser
  2. A tool call that errors shows as a failed stepbrowser
  3. A step message can carry a status, so B3 can show check resultsapi
E2

Run several sessions in a project, in a wider workspace

A project has a sessions sidebar: the architect starts a new session or switches to an older one, and the chat uses the width of the screen.

Today The database allows many sessions per project, but the web app is one project, one session: loading opens only the last-touched session and there's no way to start another. The API lists bookmarked sessions, but the web app never shows them. In UAT the workspace was too narrow.

  1. The project view lists every session, newest first, and opening one shows its own chatbrowser
  2. New session starts an empty chat, with an empty Blender file from D2browser
  3. On a 1440-pixel-wide window, the sidebar and chat together fill the width, with no fixed narrow columnbrowser
  4. The bookmark endpoints are replaced by GET /projects/{id}/sessions, and the contract is regeneratedcode

E3

Sessions name themselves from my first prompt

A fast model call on the first prompt gives the session a short title, which the architect can rename.

Today Sessions have a name column, but only the bookmark call sets it, so new sessions are unnamed.

  1. After the first prompt, the session gets a short titleapi
  2. A name typed before the title arrives is keptapi
  3. A failed title call leaves the name empty and the run unaffectedunit
