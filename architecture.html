03 · LangGraph

The LangGraph graph, which is the whole state machine

The state machine is a LangGraph StateGraph compiled in harness_state_machine.py, and these five nodes are the entire graph. Each node is a small class in harness/states/. There are no subgraphs and no checkpointer. The run is driven by astream_events, and each LangGraph event is mapped to a run-stream event as it happens. Writing the chat rows happens outside the graph, after it returns. The tags show which box of the harness model each node implements.

05 · Tags

How the agent finds and edits what it built

Every object the agent makes in Blender carries a small, fixed set of custom properties. The tags give the model a way to describe the scene and to pick out exactly the objects a follow-up prompt is about, without guessing object names. All of it lives in mcp/blender_tags.py.

Every object is tagged

level (whole number, ground = 0) and category (wall, slab, roof, window, door, column, core, stair, facade, massing, site, light, camera, other) are required. space, building, use, status and host are optional, and windows and doors always name their host. The rules are part of the system prompt.

Checked after every code call

After each execute_blender_code, a probe adds untagged_objects (up to 20) and untagged_total to the result, and the model is told to fix them straight away. If the probe fails, the result says so and the code call still counts.

An outline in every prompt

gather_info runs one probe that counts objects per level and category, plus the untagged ones, and puts the result in the system prompt (1,500 characters at most). With Blender closed, the outline is left out.

Edits go through filters

execute_blender_code takes the tag filters and name_contains. The code then runs with targets, the objects matching every filter. find_objects lists matches with their tags and world-space bounds, up to 200. targets is set fresh on every call and must never be stored between calls.
